# 譜面用 テンポ・拍グリッド解析ツール

MP3を渡して、(1) 曲中でテンポが変わるか、(2) NLMに設定するBPMと無音追加(ms)をいくつにすれば
拍グリッドが音に合うか、を調べるためのスクリプト群。最初の題材は `test-audio/` に置いた曲A（MP3）。
2曲目の題材は曲B（FLAC。後述、曲頭無音と裏拍の教訓が出た）。曲名は公開時に伏せている。

## 準備(初回のみ)

- 試験用の音源は `test-audio/` に置く(フォルダごと `.gitignore` 済み。著作物なのでコミットしない)。
- `.venv`(Visual Studio付属のPython 3.9)に `librosa` が入っている。作り直すとき:
  `py -3.9 -m venv .venv` → `.venv/Scripts/python -m pip install librosa`
- pipがSSL証明書エラーで失敗する場合、ウイルス対策ソフト等のHTTPS検査(通信の中継)が原因のことがある。
  恒久対処は `%USERPROFILE%\pip\pip.ini`(`[global] cert = %USERPROFILE%\pip\ca-bundle.pem` の絶対パス)と、
  同フォルダの `ca-bundle.pem`(pip同梱certifi + Windows証明書ストアにある、そのソフトのルート証明書)を置くこと。
  `--trusted-host` は検証を切るので使わない。
  `pip.ini` をbashの `printf` で書くと `\U` が壊れる。ヒアドキュメント(引用符付き)かエディタで書く。
- 実行は `.venv/Scripts/python tools/<script>.py <mp3>`。出力はUTF-8(スクリプト側で設定済み)。
- `tempo_leadin.py`・`analyze_structure.py` は `.venv-build`（Python 3.14・librosa 1.0）でも同じ結果で動く（下の「librosa の版を上げる時」）。
  この2つの計算は本体に同梱する `song_analysis/`（NLM の「曲を解析」・serve.py の `/__analysis/*`）にあり、tools の2つは表示だけ（2026-10-19）。
  計算を直す時は `song_analysis/tempo.py`・`song_analysis/structure.py` を直す。tools のモジュールの定数を書き換えると song_analysis にも効く。

## 進め方(別の曲でもこの順)

曲頭は無音/弱起でビート検出の精度が落ちやすく、そこを起点にBPMと無音追加を同時に手探りすると
収束しない・誤った方向へ迷い込むことがある(曲Bでの実例は後述)。そのため**曲の中央部でBPMを
確定してから、無音追加だけを逆算する**順序に変えた。

1. **`tempo_leadin.py` でBPMと無音追加を出す**（一番最初にこれを実行する）:
   ```
   .venv/Scripts/python tools/tempo_leadin.py <音源ファイル>
   ```
   BPM の系統（2倍・半分を除いた値）→ 精密化 → 無音追加、まで自動で行う。裏拍の疑い・途中の段差・
   テンポの揺れ（ライブ録音など）も知らせる（後述）。
2. **NLM に入れて耳で確かめる**。裏拍の候補A/Bが出ていたら両方聞いて合う方を選ぶ。
   ずれが気になる時は「次の一手」の `beat_grid_check.py` で1拍ごとのずれを見る。
3. **テンポの揺れ・段差の警告が出た時だけ** `beat_grid_check.py` の区間表、`analyze_tempo.py`・`tempo_drift.py` で詳しく見る。

## 各スクリプトの出力と読み方

### tempo_leadin.py — BPMと無音追加(まずこれを実行)
```
.venv/Scripts/python tools/tempo_leadin.py <音源ファイル> [--lo 75] [--hi 180]
```
（2026-10-19 に作り直した。前の方式は同じアーティストの62曲で外れが多かった＝下の「テンポの推定の作り直し」）
1. **系統を決める**: 打楽器成分の打点の強さの流れを16秒ずつ区切って周期の強さを測り、曲全体で平均する。BPM の候補ごとに
   「1倍・2倍（8分）・4倍と3倍の強い方（16分か3連符）」の強さを足し、一番大きい物を選ぶ。
2. **2倍・半分**: `--lo`〜`--hi` に入る物のうち、その周期そのものが強い方（譜面の細かさで吸収できるのでどちらでもよい）。
3. **精密にする**: 1拍ごとの打点とのずれに直線を当てはめ（Theil-Sen）、傾きが無くなるまで BPM を直す。打点を探す幅は拍の
   0.4 倍まで（速い曲で隣の拍を拾わない）。近い整数（±0.1）でも、8秒ごとのずれの中央値に傾きが無ければ整数にする
   （曲は普通 整数の BPM で作られている。段差をまたぐ組は傾きの計算に入れない）。
4. **無音追加**: 8秒ごとのずれの中央値の中央値で合わせ、30ms 足す（打点の強さの山は、耳で合わせた拍より遅く出る。
   利用者の2曲と手元の譜面5つで 17〜60ms・中央値 31ms、7件とも同じ向き）。
5. 出力の読み方:
   - 「8秒ごとの…ばらつき」: 20ms 前後までなら耳では区別できない。スタジオ録音の曲は 11ms 以下、テンポの揺れる曲は 27ms 以上だった。
   - 「2番目の候補」: 系統の違う一番の対抗。強さが 85% 以上なら迷いあり（こちらも聞く）。
   - **段差**（「0:56 あたりから +62 ms ずれる」）: その前後はそれぞれ平らで、途中で一度だけずれる（拍の長さの違う所がある等）。
     耳で確かめ、必要ならテンポパートで直す。
   - **テンポの揺れ**（20秒ごとの最適な BPM の幅が 1.5% 超）: ライブ録音・クリックなしの演奏。1つの BPM では途中から合わない。
   - **裏拍の疑い**（候補A/B）: 6秒区間の2割以上で強い打点が半拍ずれた所にある時と、低い音（キック・ベース）が半拍ずれた
     位置の方に強い時（3本の手がかりのうち2本以上）。どちらが拍の頭かは機械では決めきれないので、**両方を NLM で聞いて確かめる**。
   - `estimate(env, fps, lo, hi, low)` は一括処理からも使える（`onset_env(path)` の戻り値を渡す）。計算の本体は `song_analysis/tempo.py`。
   - 16秒より短い音源で落ちていた（周期の強さを測る区間の長さを確かめる前に窓を掛けていた）のを直した（2026-10-19。16秒以上の曲の結果は同じ）。

### analyze_tempo.py — ビート追跡による区間BPM
`区間 / 開始(秒) / 終了(秒) / 拍数 / BPM` の表。全区間が同じBPMなら一定テンポ。
librosaのビート追跡は一定テンポ寄りに解を出すので、**変化が出ないことは弱い証拠**。
BPMは80〜160に折り返して2倍・半分の誤認を無視している(譜面側でノーツを1/2に置けば済むため)。

### tempo_drift.py — 窓ごとの最適BPM
20秒窓ごとに最適BPMと、全体グリッドとの位相差(拍単位)を出す。探索範囲は `LO, HI`(75〜92)で、
想定BPM付近に絞る。絞らないと1.5倍(約125)や4/3倍(約112)の別ピークを拾って混乱する。
窓のBPMが継続的に別の値へ動く、または位相差が一方向に溜まれば変化あり。
**位相差は±0.4拍ほど平気で揺れる**(シンコペーションで支配的な打点が窓ごとに変わる)ので、
位相差を根拠にズレ量を判断してはいけない。BPMの大づかみな確認にだけ使う。

### beat_grid_check.py — 1拍ごとのズレ計測(決め手になる手法)
```
.venv/Scripts/python tools/beat_grid_check.py <音源ファイル> --bpm 83.94 --lead-ms 250
```
グリッド拍k = 元音源上の `k*60/BPM - lead` の前後±0.2秒で、パーカッシブ成分のオンセットが
最大の点を打点として、ズレ(打点−グリッド)をmsで出す。**正=音が遅い、負=音が先**。

- 「6秒ごとのズレ中央値」の表: 時間とともに一定の速さで増減 → BPMの誤差。
  ある時点で段差状に跳ぶ → テンポ変化(テンポパートで対処)。一時的な突出だけ → 無視してよい。
- 「直線当てはめ」: 傾き[ms/拍]と切片[ms]をTheil-Senで推定(外れ値に強い)。
- 「提案」: `BPM = 60 / (現周期 + 傾き)`、`無音追加 = 現在値 − 切片`。95%範囲が0をまたぐなら
  「傾きは有意でない」と出て、BPMは今のままでよい。
- 「残差の中央絶対偏差」: 当てはめ後のばらつき。20ms前後までなら耳では区別できない。

## 曲A での結果(2026-09-21)

- テンポ変化なし。約84 BPMの一定テンポ(ビート追跡の83.4、Fourier探索の83.94は推定誤差)。
- `--bpm 83.94 --lead-ms 250` では傾き -0.431 ms/拍、曲全体で約-113msの音先行ズレ
  (0:03で約0ms、1:33で約-66ms、3:00で約-130ms)。1:33あたりで人が気づく閾値を超える。
- 提案 BPM 83.991 / 無音追加 255ms。**BPM 84.00 / 無音追加 265ms** にすると、
  曲全体のズレが+6msまで縮み、傾きは有意でなくなった。

## 曲B での結果(2026-09-22)

- 曲頭(0-8秒)から `beat_grid_check.py` の反復だけで詰めようとしたところ、BPMをどんどん
  低い方へズラす沼にはまり、「テンポが曲中で変化している」と誤診断した。実際はテンポ変化なし。
- `tempo_leadin.py` で曲の中央部(45〜183秒)からBPMを確定させたところ、**BPM 129 で一定**という
  正しい結論にすぐ到達できた(区間ごとのBPMがほぼ一致、外れ値1区間は自動除外)。
- 無音追加は当初「28ms」と出たが、実測(耳で確認した正解)は**240ms**で大きく食い違った。
  6秒区間のズレを見ると、+50〜60msの区間と-150〜175msの区間が曲の構成(パート)に沿って
  ブロック状に入れ替わっており、その差(約220ms)はBPM129の半拍(約233ms)に近かった。
  → **オンセット検出が、曲のパートによって強拍/裏拍のどちらを拾うか入れ替わっていた**。
  裏拍検出ロジックを追加し、候補B(半拍ずらし)として「260ms」が出るようになった。実測240msと
  ほぼ一致(誤差20ms)。
  （2026-10-19 追記: この時の `tempo_leadin.py` は無音追加の符号が逆だった＝下の「作り直し」。今の版は 210ms を出す）

## 今回の失敗と教訓

- **符号を取り違えない**: Fourier位相 `angle(Σ env·e^{-2πift})` は、打点が `kP+τ` にあるとき `-τ` になる。
  これを打点位置として読んで無音追加を誤って提案した(170msと言ったが正しくは250〜330ms)。
  位相ではなく、打点を直接探す `beat_grid_check.py` の方式を使えば符号の混乱が起きない。
- **Fourier位相のズレ測定は使わない**: 10〜20秒窓ごとに±100〜250msも揺れ、存在しない
  「70〜106秒のズレ」を報告してしまった。ズレ量は必ず1拍ごとの直接計測で見る。
- **BPMの小数第2位が効く**: 83.94と84.00の差はわずか0.07%だが、250拍で約130msになる。
  耳で「途中から合わない」と感じたら、テンポ変化を疑う前にBPMの微調整を試す。
- **耳の証言を優先する**: 「1:33までは合っている」という感覚は、ズレが徐々に溜まって
  閾値(約60〜70ms)を超える位置と一致していた。解析結果と耳が食い違ったら、解析側を疑う。
- 探索範囲は想定BPM付近に絞る(倍数関係の別ピークを避ける)。
- **曲頭からBPMと無音追加を同時に手探りしない**(曲Bでの失敗): 曲頭は無音/弱起でビート検出の
  精度が最も低い。無音追加がズレたまま反復すると、オンセット検出が隣の拍を拾って「テンポ変化」に
  見える段差が出る。先に曲の中央部だけでBPMを確定し(`tempo_leadin.py`)、無音追加は後から逆算する。
- **「傾きが有意でない」=正解、とは限らない**: 曲によっては強拍/裏拍のどちらがオンセットとして
  強く出るかが曲中のパートで入れ替わり、ズレが基準値と半拍離れた値の間を往復する。この場合BPM自体は
  傾き0で正しく収束するが、無音追加(位相)だけは機械的に一意に決まらない。6秒区間のズレ表に
  ブロック状の符号反転がないか必ず確認し、あれば半拍ずらした候補も耳で確認する。

## テンポの推定の作り直し（2026-10-19）

同じアーティストのアルバム一式（62曲）で前の `tempo_leadin.py` を試したところ、外れが多かった。正解は手元の Beat Saber 譜面の
BPM（作者が複数いる曲は全員一致）・利用者が耳で確かめた値・構成解析の時に確かめた値の14曲（2倍・半分は同じとみなす）。

| | 系統が合った（14曲） | 8秒ごとのずれのばらつき（スタジオ録音の曲） |
|---|---|---|
| 前の方式 | 3〜4曲 | 1拍ごとの残差 80〜110ms の曲が多い（目盛りが打点に乗っていない） |
| 今の方式 | 13曲（外れはライブ録音の1曲で、正解の欄が原曲の譜面の値） | 全曲 11ms 以下（中央値 3ms） |

前の方式が外れた理由と、直した所:
- **1つの周期の強さで選んでいた**: 本当のテンポの 3/2・4/3・5/4 倍（倍音。2拍・4拍の周期の繰り返しから出る）が一番強い曲が多い。
  本当のテンポなら 2倍・4倍（8分・16分）も強いので、それを足して選ぶようにした。3連符の曲（16分が弱く3倍が強い）で
  3/4 倍を選ばないよう、4倍と3倍の強い方を数える。
- **区間ごとの値の中央値**: 区間によって 150 と 100 が半々の曲で、間の 125 という意味の無い値になっていた。
- **無音追加の符号が逆だった**: NLM の目盛りは元の音源の `k×周期 − 無音追加` にあるので、打点が目盛りより x ms 遅い時は
  無音追加を x 減らす（`beat_grid_check.py` はこの向き）。前の `tempo_leadin.py` は x をそのまま無音追加にしていて、
  曲Aでは 102ms（正しくは約 260ms）を出していた。一括処理（構成解析の 62 曲）も同じ間違いだった。
- **打点を探す幅が ±0.2 秒固定**: BPM 150 を超えると半拍より広く、隣の拍を拾った。
- **途中の段差で傾きが付く**: 途中で一度だけ拍がずれる曲（172 なのに 171.948 と出た等）は、整数の確かめを段差で区切って行い、段差を知らせる。
- 試して使わなかった物: 低い音（キック）だけで拍の頭を決める（1曲は直るが、他の曲で決め手にならない＝候補Bの案内にだけ使う）。

## 曲の構成の解析（analyze_structure.py・2026-10-19 試作）

譜面作りの下調べ用。曲の区切りと「この区間とこの区間は同じ・似ている」（グループ）を出す。メロディーを譜面に
起こすものではない。BPM と無音追加が決まった後に使う（拍の目盛りに合わせて測るため）。

```
.venv/Scripts/python tools/analyze_structure.py <音源> --nlmf <プロジェクト.nlmf>
.venv/Scripts/python tools/analyze_structure.py <音源> --bpm 84 --lead-ms 260 [--out <出力.html>] [--truth <正解.json>] [--unit 2]
```

- `--nlmf` は BPM・無音追加・テンポパート・Music の配置（`audioPosAtBeat` と同じ計算）とマーカーを読む。
  マーカー（または `--truth` の正解ファイル）があれば、それを正解とした一致率（区切り ±1拍/±2拍・グループ分けの
  ペア F 値と、±2拍の内訳＝正解を見つけた割合・出した区切りが正解に合う割合）も出す。
- 出力は音源と同じフォルダ（`--out` で変更）の `<名前>.structure.html` と `.json`。HTML は帯・一覧・地図のクリックで
  その位置から再生できる（音源は相対パスで参照するので、HTML と音源の位置関係を変えないこと）。拍は NLM の拍。
- `--unit` は1単位の拍数（下の 2.）。細切れなら大きく、粗すぎるなら小さくする。
- 1曲 15〜35 秒。
- 計算の本体は `song_analysis/structure.py`（NLM の「曲を解析」と同じ。このコマンドは .nlmf の読み込み・答え合わせ・報告だけ）。
  NLM からは目盛りを「拍 0, 0.25, … ごとの元の音源の秒」（`measure_at`）で受け取る。テンポが一定で Music を切っていなければ
  `nlm_grid` がこのコマンド（TempoMap）と同じ式で秒を作り直すので、同じ曲・同じ BPM と無音追加なら NLM とこのコマンドの結果は同じ。
  （コマの境目がフレームの境目にちょうど乗る曲が多く、秒の最後の桁が違うだけで区切りが変わることがあるため。試した曲では、
  コマの終わりの秒を最後の桁だけ違う式で出すと区切りが1つ 0.25 拍ずれ、1ms に丸めた秒ではセクションの区切りと番号がいくつか変わった）

### 仕組み

1. 拍の目盛りの4分の1拍ごとに、音色（MFCC 1〜19）と、歌の音域の音の高さ（調波成分の CQT の C4〜C6）を測る。
   各次元を曲全体（音のある所）で標準化する。
2. 比べる幅・ならす幅・区間の最短の長さは「1単位」で決める。1単位は約0.7秒（BPM 84 の1拍）に一番近い 1・2・4 拍
   （BPM 119 未満は1拍、238 未満は2拍）。拍のままだと速い曲で和音が変わるたびに区切り、細切れになった（曲B）。
3. ラプラシアン分割（McFee & Ellis 2014。「4単位ぶんの流れが似ている所」のつながり＋隣のコマとの音色の近さ）を
   グループ数 4〜12 で9回行い、区切りは多数決（4割以上）で決める。
4. 似ている長い区間（20単位以上）の組を重ね、「同じ所」と「違う所」の境目で両方を分け直す。
5. 「9回のうち半分以上で同じグループ」の隣どうしを1つにまとめ、最後に「多数決の割合」と「区間どうしを重ねた時の
   似ている度合い」の幾何平均（0.4 以上）でグループに分ける。多数決だけだと、楽器の雰囲気が近い別のパート
   （曲B の Bメロとサビの後半）が同じグループになった。
6. サビの候補は、2回以上出るグループのうち合計の長さが一番長いものと、それと交互に出るグループ（隣がサビの
   グループである回数が出てくる回数の1.5倍以上。サビの直前に毎回来るパートは含めない）。
6b. **グループの確認**（`member_check`）: 3個以上のグループで、他のどの区間とも重ねた度合いが 0.4 に届かない区間は
   外す。多数決は楽器の雰囲気が近いだけの区間も強く同じグループにする（ある曲でサビ後半のグループに Bメロ・Cメロの
   一部が混ざり、利用者が耳で「違う」とした3区間がちょうどこれで外れた。本物の組は 0.47〜0.71、混ざった物は 0.26〜0.35）。
6b2. **繰り返しを回数で表す**（`split_repeats`）: 隣り合う同じグループをつなげるので、2回続くサビ等が1本の長い区間になり
   1回分と形が変わっていた（利用者が耳で確かめた: 「同じサビが2回」が正しい）。同じグループの他の区間（8秒以上＝フレーズ）
   の 1.6〜3.4 倍の長さの区間を、1回分ごとに分ける（2回目以降の頭は相手の長さの 0.75〜1.35 倍の範囲で一番重なる所。
   各部分が 0.4 以上似ている時だけ）。全部が繰り返しでなくても、頭の1回分が 0.5 以上似ていれば頭とそれ以外に分ける。
   8秒未満の短い動機の繰り返し（間奏のメロディー等）は分けない（利用者の判断: 1つのパートとして正しい）。
6c. **セクションの段**（`build_sections`）: 細かい区切りの隣り合う2グループの組のうち、重ならずに2回以上出る物を
   1つにまとめる、をくり返す（例 B C B C → 1つ・`sections_from`）。1つの長さは 20 秒まで（24 秒だと Aメロ＋Bメロ、
   イントロ＋次のパートまでつながった）。報告では細かい区切りの上に S1・S2… の帯として出す。
   - 番号は中身で決める: 中の細かいグループの割合（長さで重み）が 0.6 以上同じ・並び順どおりに重ねて 0.45 以上似ている・
     長さの比が 0.75 以上、の組でつながった仲間に同じ番号。割合だけだと同じ部品を違う順に並べた別の Aメロまで同じ番号に
     なり、前から順に決めると後ろの仲間を介してしかつながらない区間が別の番号になった。
   - 相手の無いセクションが続く所どうしは、まとめた全体でも同じ3つの条件で比べ、合えばそれぞれ1つにまとめる（`join_runs`・
     20秒まで）。細かい区切りの割れ方が1番と2番で少し違うと、同じパート（ある曲の Bメロ）が 2つと3つに分かれて、
     どれも相手が無くなっていた（利用者が耳で「同じ」と確かめた）。
   - 1回しか出ない短い（12秒未満）セクションが続く所を、30秒まで1つにまとめる（利用者の判断: 1回しか出ない所は
     1つのパートでよい）。「1回しか出ない」は番号が1回だけで、かつ中の細かいグループの外に出る長さが中の半分未満。
   - サビの候補（報告では★）: 中身の割合だけの緩い仲間で数え、2回以上出る仲間のうち 長さ×(1＋0.15×音の大きさ
     [曲の中央値からの dB]) が最大の物。表示の番号と同じ厳しさで数えると、少し違うサビ（落ちサビ等）が別の番号に分かれて
     外れが増えた。
6d. **名前の推測**（`name_sections`）: セクションに仮の名前（イントロ/Aメロ/Bメロ/サビ/間奏/Cメロ/アウトロ）を付ける。
   作る人と遊ぶ人が同じ言葉で話すための目安。歌の有無は見ず、並び方だけで決める:
   - サビ＝サビの候補と、サビの細かいグループが半分以上を占めるセクション（★が1つの番号だけだと後半のサビを落とした）。
   - アウトロ＝最後のサビより後の曲末 30 秒まで。イントロ＝最初のサビより前の頭（頭の1つと続く1回だけの物・25 秒まで）。
   - サビの後のかたまりの頭の1つが、最初のかたまりの歌に出てこない番号なら間奏。2回目のサビより後の1回だけの物は Cメロ。
     残りの歌の区間は、かたまりの中の前の 6 割を Aメロ、残りを Bメロ。同じ番号は多数決で同じ名前にそろえる。
   - 報告ページでは番号ごとに名前を付け直せる（ページの中だけ。［名前の一覧をコピー］で控える）。
   - 38曲で、名前が合った時間の割合は平均 54%（サビの位置だけ正解から与えると 73%＝外れの多くはサビの候補の外れから）。
     間奏とCメロ・Aメロの見分けが弱い（歌の有無を見ていない）。サビとサビの間を細切れにした続け方
     （サビの直後から続けて間奏にする等）は、2番の歌まで間奏になって下がった。
7. 一覧の「似ている度合い」は、区間どうしを重ねた時の値（1単位ぶんの流れの似ている度合いの平均。±1単位ずらして最大）。
   目安: 0.7 以上「ほぼ同じ」、0.5 以上「よく似ている」。

### 正解の作り方（調整し直す時）

- 自分で譜面を作った曲は、NLM のマーカー（`--nlmf`）がそのまま正解になる。
- コード譜があれば `tools/chords_to_truth.py` で正解ファイルを作れる。コード譜を「`[セクション名]` の見出し＋1行ずつの
  コード」のテキストに書き（# で始まる行はコメント）、拍ごとの和音に動的計画法で当てはめてセクションの開始拍を出す。
  コード譜で省略された所（間奏が1行など）は1つのコードが長すぎる警告が出るので、出力の JSON を手で直す。
  コード譜のテキストと正解ファイルは音源と同じ `test-audio/` に置く（コミットしない）。
  - コード譜はカポ付きで書かれていることがあるので、既定で12通り移調して一番合うものを選ぶ（`--transpose`）。
    Cadd9・C#m7(b5)・B♭・分数コードなどは基本の形で読む（テンションは無視）。N.C. 等の読めない物は「コードなし」。
  - 当てはめは崩れやすい（似たコードが続く・同じ進行だけの曲・テンポの推定が外れている曲）。崩れた時は、1拍のコードが
    続く・1つのコードが何十拍も続くのが目印。直す手がかりは、低音の音名・音量の段差・音色・1番と2番の相関。
- 調整は1曲だけで決めない。少なくとも2曲で、片方を上げてもう片方が下がらないことを確かめる。

### librosa の版を上げる時（2026-10-19 に 0.11 → 1.0 で確かめた方法）

NLM に同梱する解析は `.venv-build`（Python 3.14）の librosa 1.0 で動く。解析を作った `.venv` は Python 3.9・librosa 0.11。
1.0 で結果が変わらないことを次の方法で確かめた（版を上げる時も同じことをする）:
- **途中の値**: 同じ音源で、読み込んだ音・打楽器/調波成分・打点の強さ・CQT・MFCC・音の大きさを両方の版で保存して比べる。
  1.0 は音・CQT・音の大きさが完全に同じ、打点の強さと MFCC が浮動小数の丸めの差だけ（最大 1e-7 割・MFCC 1.5e-5）。
- **テンポ**: 62曲＋1曲を、保存したオンセットではなく音源から両方の版で推定し直して比べる → BPM・無音追加・候補B・段差・警告が全曲同じ
  （違いは3曲の傾きの 0.0 と −0.0 だけ）。
- **構成**: 正解のある38曲＋1曲の一括採点（特徴は版ごとに測り直した別のキャッシュで）→ 曲ごとの採点・細かい区切り（区間とグループ）が全曲同じ。
  セクションの段 ±4拍 73%・合う 48%・グループ 58%・サビの候補 20/38、細かい区切り 85%・38%・56%、利用者のマーカーの曲 ±1拍 68%・グループ 74%。
- librosa 1.0 は audioread を使わない（libsndfile で読めない形式はエラー）。NLM は ffmpeg で WAV にしてから読む（`song_analysis/service.py`）。

### 試して効かなかったこと（同じ道をたどらないために）

- **和音（chroma）だけ**: 曲全体で調が同じなのでどのコマも似て見え、区間の見分けが弱い（AUC 0.89〜0.92。
  音色＋歌の音域の音の高さは 0.98）。
- **変化の強さ（Foote の新規性）・Serrà の structure features だけで区切る**: サビの中の区切りは音色が変わらないので出ない
  （±1拍 30〜50%）。
- **前向きに積んだ特徴**（コマ t に t〜t+7 を積む）: 区切りが積んだ長さの半分ほど前へずれる。積むなら中央に。
- **区間どうしを直接重ねた度合いでグループ分け**: 正解の区切りを使うと 93% と強いが、しきい値で 75%→57% と大きく揺れた。
  多数決（同じグループになった割合）は、しきい値 0.4〜0.7 でほぼ同じ結果になる。
- **長さの前提つきの動的計画法で区切る**: 改善しなかった。また、標準化に無音の部分を含めるか否かだけで区切りが
  変わったので、1曲の数字の上下に合わせた細かい調整はしない方がよい。
- **1単位を秒に比例させる**（BPM 129 で 1.5 拍など）: 曲A が 1.25〜1.5 拍で区切り ±1拍 55% に下がり、曲B も 2拍より悪かった。
  1・2・4 拍のどれかに丸める方がよい。
- **グループ分けのしきい値を上げる・最小連結にする**: どちらの曲も細かく分かれすぎて下がった。
- 以下は38曲＋曲Aで比べた（2026-10-19）。
- **細切れを単位で減らす**（単位を一律2倍・曲ごとに区間の長さの目安で 1/2/4 倍を選ぶ）: 区間は減るが本物の区切りの
  見落としが増え（±4拍 82%→65〜74%）、余計な区切りの割合は減らない。細かい区切りは残し、上にセクションの段を作る方がよい。
- **セクションの段の別案**: 少ないグループ数（3〜6）での多数決、長い幅の変化の強さで残す区切りを選ぶ、は繰り返す並びを
  まとめる案より、区切り・グループとも少し悪かった。
- **境目の前後の短い区間を消して1本に戻す**（変化の強さが一番大きい所へ）: 小節の頭との ±1拍は少し上がるが ±2・±4拍は
  下がり、曲Aのマーカー（歌の入り）とは ±1拍 68%→64% に悪化した（本物の短い区間まで消える）。
- **比べる幅（積む幅）を狭くする**（4単位→2・3単位）: 小節の頭との一致は上がる（±1拍 31%→50%）が区間が増え（29→44個）、
  グループと曲Aのマーカーとの一致が大きく下がった（±1拍 68%→44%）。
- **区切りを歌の入りへ寄せる**: REPET-SIM（`nn_filter`）で歌を分ける方法は、間奏のリード楽器も「歌」と出て使えない。
  左右の真ん中にある倍音の割合を歌の目印にし、境目の2本の真ん中の ±1.5拍に歌の入りがある時だけ1本にする方法は、
  悪くする曲がほとんど無いが改善も小さい（曲A ±1拍 68%→70%、38曲の小節の頭 ±1拍 121→129個/473個）。
  真ん中のリード楽器を歌と取り違える・モノラル音源では使えない・フレーズの中の息継ぎと区別できない、が弱点。（未組み込み）

## エディタを自動で動かして検証する（cdp.py / fixtures/）

`tools/cdp.py` はヘッドレスEdgeでエディタを開き、スクリーンショット・本物のマウス/キー入力・JS実行を行う
（標準ライブラリだけでDevTools Protocolを話す。Node/Playwright不要）。3Dビューも写る（画面は出さずにGPUで描画。
GPUが無いPCではソフトウェア描画になる。環境変数 `NLM_TEST_SOFTWARE_GL=1` でソフトウェア描画に固定できる）。

```
.venv-build/Scripts/python.exe tools/cdp.py shot out.png --fixture basic   # テスト素材を開いて撮影
.venv-build/Scripts/python.exe tools/cdp.py eval "window._dbgApp.state()"  # 状態をJSONで表示
```

Pythonから使う場合（検証スクリプトの書き方）はファイル冒頭の説明を参照。要点:
- ページは `editor.html?dev=1` で開くので、開発用窓口 `window._dbgApp`（読み取り専用。状態・未保存判定・
  マスの画面座標`cellScreen(x,y)`など）と `window._dbg`（ランタイム全体）が使える。どちらも配布版では作られない。
- 設定の保存先は一時フォルダ（手元の `config/settings.json` は汚さない）。`Editor(keep_data=True)` で残せる。
  起動時にそこへ初期値（`config/settings.default.json`）＋`Editor.TEST_SETTINGS` を書く（`bsnm_anaAsk='0'`＝曲を読み込んでも「曲を解析しますか？」を
  出さない。撮影・検証で曲を読むたびに出ないように）。その画面を撮る時は `localStorage.removeItem('bsnm_anaAsk')` してから曲を読む。
  `bsnm_anaGuide='0'` も同じ（解析が終わっても「次にやること」の案内を出さない。撮る時は `localStorage.removeItem('bsnm_anaGuide')` してから解析する）。
- serve.py は合言葉（`X-NLM-Token`）を求める。ページは `ed.url()`（合言葉 `#k=…` 付き）で開けばアプリが自動で付ける。
  Python から直接サーバーへ要求する時は `headers={"X-NLM-Token": ed.token}` を付ける。補助タブ（`new_tab`）は自動で付く。
- `ed.errors()` でページ内の例外・console.errorを回収できる。検証の最後に空であることを確認する。
- 3Dビューの表示状態など「描画ループで更新される値」を見る検証では、`ed.frames()` が0でないこと
  （描画ループが動いていること）も確認する。ヘッドレスはバックグラウンド扱いで描画が止まることがあり、
  cdp.py 側で抑制を切っているが、止まっていると古い値のまま判定を誤る。
- exe版固有の動き（×ボタンの確認ダイアログ・ネイティブのファイル選択）はブラウザでは再現できない。

テスト素材 `tools/fixtures/`:
- `basic.wav`: 120BPM・16秒のクリック音（プログラム生成＝著作物の問題なし）
- `basic.nlmf`: basic.wav 用のプロジェクト（1〜8拍目に赤青ノーツ8個）。`Editor(fixture='basic')` で開ける
- `rich.nlmf`: 主要な要素を一通り含む素材（2難易度・ボム・壁・アーク・チェーン・ライト・BPM変化）。元は `rich_map/`
  （Beat Saber の譜面フォルダ）で、アプリの「曲データを読み込む」で読ませて保存させたもの。音源は basic.wav を使い回す
- `make_fixtures.py`: 上の素材を作り直す。nlmf はアプリ自身に保存させている＝保存形式が変わったらこれを実行すれば追従する。
- `media_lib/`・`make_media_lib.py`: MEDIA の「記録したライブラリ」のテスト用の小さなライブラリ（4曲・音楽1・画像1）と、その作り直し。
  画面で試す時は、データフォルダの `config/library.json` に `{"libs":[{"path":"<media_lib の絶対パス>"}]}` を書いて開く（JS から記録を増やす口は無い）

決まった確認はテスト（`tests/`・`tools/run_tests.py`）にする。使い方は `tests/README.md`。

テストがまれに落ちる時の切り分けには `test_diag.py`（開き直しの食い違い `reload`・ファイルのロック `files`・
ローカルサーバーの接続のあふれ `burst` の3つの実験）。経緯と過去の結果は `tests/README.md` の「たまに出るエラーの記録」。

## 譜面チェックを原作と突き合わせる（mapcheck_difftest.py）

`js/mapcheck/mapcheck.js`（譜面チェック・BeatLeader基準）は BS Map Check の移植。原作の判定が変わった時や
移植を直した時は、これで原作サイトと同じ結果になるかを確かめる（ffmpeg とネット接続が必要）。

```
.venv-build/Scripts/python.exe tools/mapcheck_difftest.py 1 2 3 7 23   # seedごとに乱数譜面を作って比較
```

- 乱数で問題の多い譜面（5難易度）を作り、原作サイトをヘッドレスEdgeで開いてプリセット「BeatLeader」で読ませた結果と、
  移植版の結果を「項目名（英語）→指摘された拍の集合」で比べる。`seed%3==2` はv3環境（Weave）、`seed%4==3` はv2形式の.dat。
- 原作は読み込み時にデータ形式を検査し、範囲外の値（回転イベントの e=2 など）があると譜面ごと読まない。生成する値は形式上正しい範囲に収めること。
- 既知の差はファイル冒頭に書いてある（原作が例外で項目ごと出さないケース）。それ以外の差は移植のずれ。

## NLM版 BeatLeader評価リストの自己テスト（blcriteria_test.py）

`js/mapcheck/blcriteria.js`（譜面チェックの2つ目のタブ）は、BeatLeader公式の文章の基準を項目番号どおりに判定する
NLM独自の実装（BS Map Check の移植ではないので、原作と突き合わせる相手が無い）。問題の無い譜面を1つ作り、
違反を1つずつ仕込んで該当項目が「違反/要確認」になるかを確かめる。判定を直した時・基準の改訂に追従した時に実行する。

```
.venv-build/Scripts/python.exe tools/blcriteria_test.py      # -v で全ケースの結果を表示
```

## チュートリアルの画像を撮り直す（make_tutorial_shots.py）

`docs/tutorial.md` の画像（`docs/images/tutorial/*.png`）は、`tools/make_tutorial_shots.py` が空の状態から
basic.wav を読み込み、実際のクリック・キー入力でノーツやライトを置きながら撮影したもの。UIを変えたら実行し直す。

```
.venv-build/Scripts/python.exe tools/make_tutorial_shots.py          # 全部撮る（約3分）
.venv-build/Scripts/python.exe tools/make_tutorial_shots.py 05 06    # 番号を指定するとその画像だけ保存（操作は最初から全部行う）
.venv-build/Scripts/python.exe tools/make_tutorial_shots.py --en     # 英語表示で撮って docs/images/tutorial-en/ へ（英語版 docs/tutorial.en.md 用）
```

- 画面の文言で要素を探す所（書き出しボタン・右クリックメニューの項目など）は、`TEXT_EN` の表で英語の文言に置き換えて探す。
  画面の文言を変えた時は、この表（lang/en.json と同じ文言）も直す。

- 赤枠と番号は撮影直前にページへ重ねた印。対象はCSSセレクタで指定しているので、配置が多少変わっても追従する。
- ファイル/フォルダ選択は差し替えてある（音源=basic.wav、画像=その場で描いたカバー、出力先・保存先=ブラウザ内の仮想フォルダOPFS）。
  書き出し・保存は実際に行われ、書き出し結果に `Info.dat`・`song.egg` が無ければ失敗として止まる（ffmpegが必要）。
- 3Dビュー内のノーツ・ライトの位置は `_dbgApp.cellScreen` / `objScreen` / `lightLaneScreen` で取っている。
- 「曲を解析」（04b テンポの確認の画面・04c 解析中の知らせ・04d 解析が終わった時の案内）は、解析の応答を自動テストと同じ偽物
  （`tests/_lib/analysis_helpers.py` の `ana_mock`）にして、見本の結果（テンポ＝`TEMPO_BASIC`・構成＝`analysis_helpers.STRUCT`）で撮る
  （合成音を本当に解析すると今の設定と同じ結果になり、確認の画面が出ないため）。04c は構成の解析の進み具合の応答を `waitFor` で止めて撮る。
  04d の案内を閉じた後は、出た帯を Ctrl+Z で消す（後の画像を前と同じ、帯の無い状態で撮る）。
- 曲を取り込んだ時の「曲を解析しますか？」（02b）と、解析が終わった時の「次にやること」の案内（04d）は、撮影の環境では出ない
  （`tools/cdp.py` の `Editor.TEST_SETTINGS` が `bsnm_anaAsk`・`bsnm_anaGuide` を `'0'` にするため）。撮る直前に localStorage のキーを消して出す
  （`analysis_helpers.ask_on`・`guide_on`。初めて使う人と同じになる）。02b は撮った後に［今はしない］で閉じる。
- 配置モードで Ctrl+←（スタートへ）を使うと定位置カメラがずれるため、スクリプトでは ← を繰り返して戻している。
- ヘッドレスEdgeは、右端のレベルメーター目盛りの位置に丸いアイコンを時々重ねて描く（DOMに無くページ側から消せない）。
  そのため撮影範囲は右端（x=1838）の手前までにしている。

### 画面の中の案内の画像（make_guide_shots.py）

アプリの画面の中に出す案内に入れる画像（`guide/*.png`。serve.py の `PUBLIC_DIRS`・exe には `nlm.spec` の datas で入る）は
`tools/make_guide_shots.py` が撮る。今は「曲の解析が終わりました ― 次にやること」の案内（`js/analysis/song-analysis.js` の `showGuide`）の、
解析の帯と溝の［🧩 クリップを作る］（赤枠）の画像だけ（`guide/ana-clips-btn-ja.png`・`guide/ana-clips-btn-en.png`・約540×130）。

```
.venv-build/Scripts/python.exe tools/make_guide_shots.py        # 日英とも撮る（約30秒）
.venv-build/Scripts/python.exe tools/make_guide_shots.py en     # 英語だけ
```

- 素材 basic と、自動テストと同じ偽の解析の応答（`tests/_lib/analysis_helpers.py`・テンポは今と同じ・構成は見本）で撮る。赤枠は撮影の直前に重ねた印。
- どちらの画像を出すかは訳の `ana.guide.img`（`lang/*.json`。`guide/` の .png の名前だけを受け付ける）。言語を足す時は、その言語で撮って名前を訳に書く。
- 帯・溝のボタンの見た目・文言を変えたら撮り直す。画像が読めない時、案内は図を外して文だけで出す。

### 上級編（make_advanced_shots.py）

`docs/tutorial-advanced.md` の画像（`docs/images/tutorial-advanced/<章>-<連番>-<内容>.png`）は `tools/make_advanced_shots.py`。
basic.wav に赤青のノーツを置き、マーカー・テンポパート・ライト・2つ目の書き出しノードを足しながら、各章の画面を撮る。
撮影の部品（赤枠・ノーツ配置・ダイアログの差し替え）は make_tutorial_shots.py のものを読み込んで使う。

```
.venv-build/Scripts/python.exe tools/make_advanced_shots.py          # 全部撮る（約6〜7分）
.venv-build/Scripts/python.exe tools/make_advanced_shots.py 03 09    # 章番号を指定するとその章の画像だけ保存（操作は最初から全部行う）
.venv-build/Scripts/python.exe tools/make_advanced_shots.py --en     # 英語表示で撮って docs/images/tutorial-advanced-en/ へ
```

- NLE の帯（目盛り・テンポパート・マーカー・レーン）はキャンバスに直接描くので、位置は `_dbgApp.nleScreen(拍)` で取る。
- パイメニューはキーを押している間だけ出るので、CDP で keyDown だけ送って撮り、撮った後に keyUp する。
- パネル（譜面チェック・難易度を測る。9章）は画面右端に出て撮影範囲からはみ出すので、撮る前に左へ寄せている。
- 3章の単独編集（03-2b・03-2c）と6章の曲を解析（06-1〜06-8）は、別の起動で撮る（クリップの色・マーカーの番号の続きなど、
  他の画像の状態を変えないため）。曲を解析は基本編の 04b と同じく偽の応答（`ana_mock`）と見本の結果（`TEMPO_SHOT`・`STRUCT_SHOT`）で撮る。
  解析からクリップを作る（06-7 確認の画面・06-8 作った後の NLE）は、帯がある間（06-6 の後・帯を Ctrl+Z で消す前）に撮り、Ctrl+Z 1回で元に戻す。
  3章のリンクしたクリップ（03-2d〜03-2h。03-2h は親を Delete →［キャンセル］で取り消す）と4章の転送の確認（04-2）も、この別の起動の最後に撮る
  （名前を付けた「サビ」を親にしたリンクを作るため）。
  新規作成のノーツのレーンが1本なので、単独編集（03-2b・03-2c）は溝の右クリックで一番上にレーンを足してから撮り、Ctrl+Z で戻す。
  「曲を解析しますか？」（06-1b）と解析後の案内（06-3b）は、基本編と同じく `analysis_helpers.ask_on`/`guide_on` で出し、撮った後に `'0'` へ戻す。
  10-1（環境設定）は「曲の解析」のチェックを表示だけオンにし、欄をスクロールして撮る。
- 「難易度を測る」は nlm-rating プラグインが要る。取り込み済みの `plugins/rating`（`current.json` と版のフォルダ）を
  環境変数 `NLM_RATING_DIR` で指定する（省略時は配布フォルダ `NLM-app/plugins/rating`）。撮影用の一時データフォルダへ
  コピーして使う。見つからなければ「プラグイン未導入」の画面を撮る。
- MEDIA ライブラリ（3章の 03-3〜03-8・10章の 10-2）は MEDIA の幅を変えるので最後に撮る。素材は自動テストと同じ `tools/fixtures/media_lib`
  （架空の曲）を一時フォルダの `CustomLevels` へ写し、撮影用のデータフォルダの `config/library.json` に記録して読み直させる
  （`tests/_lib/e2e_helpers.py` の `media_lib_load` 等を読み込んで使う。tests/ 側は変えない）。ネットへは出ない（`NLM_NO_NET=1`）ので、
  全曲データ・NLM推定の★は見本の値（`SAMPLE_DETAILS`・`media_lib_sample_extra`）、プレイ記録は見本の `PlayerData.dat` を書いて使う。
  環境設定のプレイ記録の場所は一時フォルダ（PC のユーザー名を含む）になるので、撮る前に例の文字（`C:\Users\YourName\...`）に置き換える。
  ［ファイルを選ぶ…］のある exe 版の表示にするため、撮る間だけ `window.pywebview` にプレイ記録の選択だけを置く。
- 撮った後は、画像を目で見て番号の重なり・はみ出しが無いか確かめる（画面の配置が変わると番号の位置がずれることがある）。

## ビルドして配布フォルダへ反映する

`python tools/build_and_deploy.py`（venvのPythonでも通常のPythonでも可。ビルド自体は`.venv-build`を使う）。
PyInstallerでビルド後、配布フォルダ`NLM-app/`の`exe`と`_internal`だけを差し替える
（`asset/` `config/`は触らない。`lang/`はソースの`*.json`で上書きし、旧版は退避に含める）。旧版は`_backup_before_update_日時/`へ退避し、新しい順に5個だけ残して古いものは自動削除する。
アプリが起動中なら警告して終了するので、画面を閉じてから再実行する。`--skip-build`で既存の`dist/`を反映のみ、`--no-backup`で退避なし。

- **`python`コマンドが反応しない場合**: 環境によっては`python`がMicrosoft Storeの実体のない
  エイリアス(`WindowsApps\python.exe`)を指しており、`Python`とだけ出力して即終了し、スクリプトの
  実行自体に到達しない(2026-09-22に発覚)。これはOS側でコマンドが解決される前の問題なので、
  スクリプト側では対処不可能。`py tools/build_and_deploy.py`(Python Launcher経由)か、
  `.venv-build/Scripts/python.exe tools/build_and_deploy.py`(フルパス指定)を使う。
  なお、`.venv-build`以外の実在するPython(システムPython・別のvenv等)で起動した場合は、
  スクリプト内部で自動的に`.venv-build`のPythonへ再実行する仕組みを入れてあるので、
  上記2つのどちらかが動きさえすれば以後は気にしなくてよい。

## リリース用のファイルを作る（make_release.py）と自動更新の自己テスト（update_test.py）

`python tools/make_release.py` — ビルド後（`dist/NonLinearMapper`）に実行し、GitHub リリースに添付する
`dist/release/NonLinearMapper-<版>.zip` と `dist/release/update.json` を作る。update.json はアプリ内の自動更新
（`app_update.py`）が最新リリースから読むファイルで、zip の SHA-256・サイズと、`CHANGELOG.md`/`CHANGELOG.en.md` の
各版の太字の見出し（更新のお知らせに出る）が入る。APP_VERSION・ビルド結果・CHANGELOG の先頭の版が揃っていないと止まる。
**リリースには zip と update.json の両方を添付すること**（update.json が無いと、旧版のアプリに更新が知らされない）。

`python tools/update_test.py` — ネットに繋がず、ローカルの偽の配布元で自動更新を通しで確かめる
（更新内容の絞り込み・SHA-256 照合・改ざん/zip slip の拒否・差し替え・失敗時の復元・利用者データを触らないこと・更新後の片付け・CHANGELOG の日英の対応）。
本物の exe の差し替え役は `NonLinearMapper.exe --apply-update --target <配布フォルダ> --pid 0 --lang ja --no-launch`
（`<配布フォルダ>/_update/new/NonLinearMapper/` に置いた exe から起動する）で単体で試せる。
