# 譜面用 テンポ・拍グリッド解析ツール

MP3を渡して、(1) 曲中でテンポが変わるか、(2) NLMに設定するBPMと無音追加(ms)をいくつにすれば
拍グリッドが音に合うか、を調べるためのスクリプト群。最初の題材は `test-audio/` に置いた曲A（MP3）。
2曲目の題材は曲B（FLAC。後述、曲頭無音と裏拍の教訓が出た）。曲名は公開時に伏せている。

## 準備(初回のみ)

- 試験用の音源は `test-audio/` に置く(フォルダごと `.gitignore` 済み。著作物なのでコミットしない)。
- `.venv`(Visual Studio付属のPython 3.9)に `librosa` が入っている。作り直すとき:
  `py -3.9 -m venv .venv` → `.venv/Scripts/python -m pip install librosa`
- pipがSSL証明書エラーで失敗する場合、ウイルス対策ソフト等のHTTPS検査(通信の中継)が原因のことがある。
  恒久対処は `%USERPROFILE%\pip\pip.ini`(`[global] cert = %USERPROFILE%\pip\ca-bundle.pem` の絶対パス)と、
  同フォルダの `ca-bundle.pem`(pip同梱certifi + Windows証明書ストアにある、そのソフトのルート証明書)を置くこと。
  `--trusted-host` は検証を切るので使わない。
  `pip.ini` をbashの `printf` で書くと `\U` が壊れる。ヒアドキュメント(引用符付き)かエディタで書く。
- 実行は `.venv/Scripts/python tools/<script>.py <mp3>`。出力はUTF-8(スクリプト側で設定済み)。

## 進め方(別の曲でもこの順)

曲頭は無音/弱起でビート検出の精度が落ちやすく、そこを起点にBPMと無音追加を同時に手探りすると
収束しない・誤った方向へ迷い込むことがある(曲Bでの実例は後述)。そのため**曲の中央部でBPMを
確定してから、無音追加だけを逆算する**順序に変えた。

1. **`tempo_leadin.py` でBPM確定と無音追加の初期値を出す**（一番最初にこれを実行する）:
   ```
   .venv/Scripts/python tools/tempo_leadin.py <音源ファイル>
   ```
   曲の中央部を複数区間に分けてBPMを検出(外れ値は自動除外)→精密化→無音追加を逆算、まで自動で行う。
   往復するズレが検出されたら「裏拍の疑い」として候補A/Bの両方を提示する(後述)。
2. **`beat_grid_check.py` で最終決定**: 1で出た「次の一手」のコマンドをそのまま実行し、
   出力の「提案」のBPMと無音追加をNLMに入れて再度流し、傾きが有意でなくなることを確認する。
   裏拍候補が出ていた場合は、候補A/Bそれぞれで実行して、耳で聞いて合う方を選ぶ。
3. **テンポ変化が疑われる場合だけ** `analyze_tempo.py` と `tempo_drift.py` で詳細確認する
   （`tempo_leadin.py`が「区間ごとのBPMのばらつきが大きい」と警告した場合、またはbeat_grid_check.py
   の区間表で段差状のズレが残る場合）。

## 各スクリプトの出力と読み方

### tempo_leadin.py — BPM確定と無音追加の逆算(まずこれを実行)
```
.venv/Scripts/python tools/tempo_leadin.py <音源ファイル> [--lo 75] [--hi 180] [--segments 4] [--center 0.6]
```
1. 曲の中央 `--center` 割合(既定60%)を `--segments` 分割(既定4)し、区間ごとにFourier探索でBPMを出す。
   中央絶対偏差(MAD)基準で外れ値(倍音・半音の誤認)を除外してから中央値を採用BPMとする。
   採用区間内でも幅が1.0を超える場合は「テンポ変化の可能性」を警告する。
2. そのBPMで無音追加0msのグリッドを仮定し、曲全体(曲頭含む)を`beat_grid_check.py`と同じ方式で
   測定・Theil-Sen当てはめし、傾きが有意でなくなるまでBPMを追い込む(最大4回反復)。
   収束後の切片がそのまま「追加すべき無音の量」になる。
3. **裏拍(半周期ズレ)の検出**: 6秒区間ごとの中央値が、基準値から「半拍」離れた位置に
   一定割合(20%以上)集まっていたら警告し、無音追加の候補A(そのまま)と候補B(半拍ずらし)の
   両方を提示する。曲によっては強拍/裏拍のどちらがオンセットとして強く出るかが曲中で入れ替わり、
   機械的にはどちらが正しいか判定できないため、**必ず両方をNLMで聞いて確認する**こと。

### analyze_tempo.py — ビート追跡による区間BPM
`区間 / 開始(秒) / 終了(秒) / 拍数 / BPM` の表。全区間が同じBPMなら一定テンポ。
librosaのビート追跡は一定テンポ寄りに解を出すので、**変化が出ないことは弱い証拠**。
BPMは80〜160に折り返して2倍・半分の誤認を無視している(譜面側でノーツを1/2に置けば済むため)。

### tempo_drift.py — 窓ごとの最適BPM
20秒窓ごとに最適BPMと、全体グリッドとの位相差(拍単位)を出す。探索範囲は `LO, HI`(75〜92)で、
想定BPM付近に絞る。絞らないと1.5倍(約125)や4/3倍(約112)の別ピークを拾って混乱する。
窓のBPMが継続的に別の値へ動く、または位相差が一方向に溜まれば変化あり。
**位相差は±0.4拍ほど平気で揺れる**(シンコペーションで支配的な打点が窓ごとに変わる)ので、
位相差を根拠にズレ量を判断してはいけない。BPMの大づかみな確認にだけ使う。

### beat_grid_check.py — 1拍ごとのズレ計測(決め手になる手法)
```
.venv/Scripts/python tools/beat_grid_check.py <音源ファイル> --bpm 83.94 --lead-ms 250
```
グリッド拍k = 元音源上の `k*60/BPM - lead` の前後±0.2秒で、パーカッシブ成分のオンセットが
最大の点を打点として、ズレ(打点−グリッド)をmsで出す。**正=音が遅い、負=音が先**。

- 「6秒ごとのズレ中央値」の表: 時間とともに一定の速さで増減 → BPMの誤差。
  ある時点で段差状に跳ぶ → テンポ変化(テンポパートで対処)。一時的な突出だけ → 無視してよい。
- 「直線当てはめ」: 傾き[ms/拍]と切片[ms]をTheil-Senで推定(外れ値に強い)。
- 「提案」: `BPM = 60 / (現周期 + 傾き)`、`無音追加 = 現在値 − 切片`。95%範囲が0をまたぐなら
  「傾きは有意でない」と出て、BPMは今のままでよい。
- 「残差の中央絶対偏差」: 当てはめ後のばらつき。20ms前後までなら耳では区別できない。

## 曲A での結果(2026-09-21)

- テンポ変化なし。約84 BPMの一定テンポ(ビート追跡の83.4、Fourier探索の83.94は推定誤差)。
- `--bpm 83.94 --lead-ms 250` では傾き -0.431 ms/拍、曲全体で約-113msの音先行ズレ
  (0:03で約0ms、1:33で約-66ms、3:00で約-130ms)。1:33あたりで人が気づく閾値を超える。
- 提案 BPM 83.991 / 無音追加 255ms。**BPM 84.00 / 無音追加 265ms** にすると、
  曲全体のズレが+6msまで縮み、傾きは有意でなくなった。

## 曲B での結果(2026-09-22)

- 曲頭(0-8秒)から `beat_grid_check.py` の反復だけで詰めようとしたところ、BPMをどんどん
  低い方へズラす沼にはまり、「テンポが曲中で変化している」と誤診断した。実際はテンポ変化なし。
- `tempo_leadin.py` で曲の中央部(45〜183秒)からBPMを確定させたところ、**BPM 129 で一定**という
  正しい結論にすぐ到達できた(区間ごとのBPMがほぼ一致、外れ値1区間は自動除外)。
- 無音追加は当初「28ms」と出たが、実測(耳で確認した正解)は**240ms**で大きく食い違った。
  6秒区間のズレを見ると、+50〜60msの区間と-150〜175msの区間が曲の構成(パート)に沿って
  ブロック状に入れ替わっており、その差(約220ms)はBPM129の半拍(約233ms)に近かった。
  → **オンセット検出が、曲のパートによって強拍/裏拍のどちらを拾うか入れ替わっていた**。
  裏拍検出ロジックを追加し、候補B(半拍ずらし)として「260ms」が出るようになった。実測240msと
  ほぼ一致(誤差20ms)。

## 今回の失敗と教訓

- **符号を取り違えない**: Fourier位相 `angle(Σ env·e^{-2πift})` は、打点が `kP+τ` にあるとき `-τ` になる。
  これを打点位置として読んで無音追加を誤って提案した(170msと言ったが正しくは250〜330ms)。
  位相ではなく、打点を直接探す `beat_grid_check.py` の方式を使えば符号の混乱が起きない。
- **Fourier位相のズレ測定は使わない**: 10〜20秒窓ごとに±100〜250msも揺れ、存在しない
  「70〜106秒のズレ」を報告してしまった。ズレ量は必ず1拍ごとの直接計測で見る。
- **BPMの小数第2位が効く**: 83.94と84.00の差はわずか0.07%だが、250拍で約130msになる。
  耳で「途中から合わない」と感じたら、テンポ変化を疑う前にBPMの微調整を試す。
- **耳の証言を優先する**: 「1:33までは合っている」という感覚は、ズレが徐々に溜まって
  閾値(約60〜70ms)を超える位置と一致していた。解析結果と耳が食い違ったら、解析側を疑う。
- 探索範囲は想定BPM付近に絞る(倍数関係の別ピークを避ける)。
- **曲頭からBPMと無音追加を同時に手探りしない**(曲Bでの失敗): 曲頭は無音/弱起でビート検出の
  精度が最も低い。無音追加がズレたまま反復すると、オンセット検出が隣の拍を拾って「テンポ変化」に
  見える段差が出る。先に曲の中央部だけでBPMを確定し(`tempo_leadin.py`)、無音追加は後から逆算する。
- **「傾きが有意でない」=正解、とは限らない**: 曲によっては強拍/裏拍のどちらがオンセットとして
  強く出るかが曲中のパートで入れ替わり、ズレが基準値と半拍離れた値の間を往復する。この場合BPM自体は
  傾き0で正しく収束するが、無音追加(位相)だけは機械的に一意に決まらない。6秒区間のズレ表に
  ブロック状の符号反転がないか必ず確認し、あれば半拍ずらした候補も耳で確認する。

## エディタを自動で動かして検証する（cdp.py / fixtures/）

`tools/cdp.py` はヘッドレスEdgeでエディタを開き、スクリーンショット・本物のマウス/キー入力・JS実行を行う
（標準ライブラリだけでDevTools Protocolを話す。Node/Playwright不要）。3Dビューもソフトウェア描画で写る。

```
.venv-build/Scripts/python.exe tools/cdp.py shot out.png --fixture basic   # テスト素材を開いて撮影
.venv-build/Scripts/python.exe tools/cdp.py eval "window._dbgApp.state()"  # 状態をJSONで表示
```

Pythonから使う場合（検証スクリプトの書き方）はファイル冒頭の説明を参照。要点:
- ページは `editor.html?dev=1` で開くので、開発用窓口 `window._dbgApp`（読み取り専用。状態・未保存判定・
  マスの画面座標`cellScreen(x,y)`など）と `window._dbg`（ランタイム全体）が使える。どちらも配布版では作られない。
- 設定の保存先は一時フォルダ（手元の `config/settings.json` は汚さない）。`Editor(keep_data=True)` で残せる。
- `ed.errors()` でページ内の例外・console.errorを回収できる。検証の最後に空であることを確認する。
- 3Dビューの表示状態など「描画ループで更新される値」を見る検証では、`ed.frames()` が0でないこと
  （描画ループが動いていること）も確認する。ヘッドレスはバックグラウンド扱いで描画が止まることがあり、
  cdp.py 側で抑制を切っているが、止まっていると古い値のまま判定を誤る。
- exe版固有の動き（×ボタンの確認ダイアログ・ネイティブのファイル選択）はブラウザでは再現できない。

テスト素材 `tools/fixtures/`:
- `basic.wav`: 120BPM・16秒のクリック音（プログラム生成＝著作物の問題なし）
- `basic.nlmf`: basic.wav 用のプロジェクト（1〜8拍目に赤青ノーツ8個）。`Editor(fixture='basic')` で開ける
- `make_fixtures.py`: 上の2つを作り直す。nlmf は cdp.py で実際にクリックして置き、アプリ自身に保存させている
  ＝保存形式が変わったらこれを実行すれば追従する。

## 譜面チェックを原作と突き合わせる（mapcheck_difftest.py）

`js/mapcheck/mapcheck.js`（譜面チェック・BeatLeader基準）は BS Map Check の移植。原作の判定が変わった時や
移植を直した時は、これで原作サイトと同じ結果になるかを確かめる（ffmpeg とネット接続が必要）。

```
.venv-build/Scripts/python.exe tools/mapcheck_difftest.py 1 2 3 7 23   # seedごとに乱数譜面を作って比較
```

- 乱数で問題の多い譜面（5難易度）を作り、原作サイトをヘッドレスEdgeで開いてプリセット「BeatLeader」で読ませた結果と、
  移植版の結果を「項目名（英語）→指摘された拍の集合」で比べる。`seed%3==2` はv3環境（Weave）、`seed%4==3` はv2形式の.dat。
- 原作は読み込み時にデータ形式を検査し、範囲外の値（回転イベントの e=2 など）があると譜面ごと読まない。生成する値は形式上正しい範囲に収めること。
- 既知の差はファイル冒頭に書いてある（原作が例外で項目ごと出さないケース）。それ以外の差は移植のずれ。

## NLM版 BeatLeader評価リストの自己テスト（blcriteria_test.py）

`js/mapcheck/blcriteria.js`（譜面チェックの2つ目のタブ）は、BeatLeader公式の文章の基準を項目番号どおりに判定する
NLM独自の実装（BS Map Check の移植ではないので、原作と突き合わせる相手が無い）。問題の無い譜面を1つ作り、
違反を1つずつ仕込んで該当項目が「違反/要確認」になるかを確かめる。判定を直した時・基準の改訂に追従した時に実行する。

```
.venv-build/Scripts/python.exe tools/blcriteria_test.py      # -v で全ケースの結果を表示
```

## チュートリアルの画像を撮り直す（make_tutorial_shots.py）

`docs/tutorial.md` の画像（`docs/images/tutorial/*.png`）は、`tools/make_tutorial_shots.py` が空の状態から
basic.wav を読み込み、実際のクリック・キー入力でノーツやライトを置きながら撮影したもの。UIを変えたら実行し直す。

```
.venv-build/Scripts/python.exe tools/make_tutorial_shots.py          # 全部撮る（約3分）
.venv-build/Scripts/python.exe tools/make_tutorial_shots.py 05 06    # 番号を指定するとその画像だけ保存（操作は最初から全部行う）
```

- 赤枠と番号は撮影直前にページへ重ねた印。対象はCSSセレクタで指定しているので、配置が多少変わっても追従する。
- ファイル/フォルダ選択は差し替えてある（音源=basic.wav、画像=その場で描いたカバー、出力先・保存先=ブラウザ内の仮想フォルダOPFS）。
  書き出し・保存は実際に行われ、書き出し結果に `Info.dat`・`song.egg` が無ければ失敗として止まる（ffmpegが必要）。
- 3Dビュー内のノーツ・ライトの位置は `_dbgApp.cellScreen` / `objScreen` / `lightLaneScreen` で取っている。
- 配置モードで Ctrl+←（スタートへ）を使うと定位置カメラがずれるため、スクリプトでは ← を繰り返して戻している。
- ヘッドレスEdgeは、右端のレベルメーター目盛りの位置に丸いアイコンを時々重ねて描く（DOMに無くページ側から消せない）。
  そのため撮影範囲は右端（x=1838）の手前までにしている。

## ビルドして配布フォルダへ反映する

`python tools/build_and_deploy.py`（venvのPythonでも通常のPythonでも可。ビルド自体は`.venv-build`を使う）。
PyInstallerでビルド後、配布フォルダ`NLM-app/`の`exe`と`_internal`だけを差し替える
（`asset/` `config/`は触らない。`lang/`はソースの`*.json`で上書きし、旧版は退避に含める）。旧版は`_backup_before_update_日時/`へ退避し、新しい順に5個だけ残して古いものは自動削除する。
アプリが起動中なら警告して終了するので、画面を閉じてから再実行する。`--skip-build`で既存の`dist/`を反映のみ、`--no-backup`で退避なし。

- **`python`コマンドが反応しない場合**: 環境によっては`python`がMicrosoft Storeの実体のない
  エイリアス(`WindowsApps\python.exe`)を指しており、`Python`とだけ出力して即終了し、スクリプトの
  実行自体に到達しない(2026-09-22に発覚)。これはOS側でコマンドが解決される前の問題なので、
  スクリプト側では対処不可能。`py tools/build_and_deploy.py`(Python Launcher経由)か、
  `.venv-build/Scripts/python.exe tools/build_and_deploy.py`(フルパス指定)を使う。
  なお、`.venv-build`以外の実在するPython(システムPython・別のvenv等)で起動した場合は、
  スクリプト内部で自動的に`.venv-build`のPythonへ再実行する仕組みを入れてあるので、
  上記2つのどちらかが動きさえすれば以後は気にしなくてよい。

## リリース用のファイルを作る（make_release.py）と自動更新の自己テスト（update_test.py）

`python tools/make_release.py` — ビルド後（`dist/NonLinearMapper`）に実行し、GitHub リリースに添付する
`dist/release/NonLinearMapper-<版>.zip` と `dist/release/update.json` を作る。update.json はアプリ内の自動更新
（`app_update.py`）が最新リリースから読むファイルで、zip の SHA-256・サイズと、`CHANGELOG.md`/`CHANGELOG.en.md` の
各版の太字の見出し（更新のお知らせに出る）が入る。APP_VERSION・ビルド結果・CHANGELOG の先頭の版が揃っていないと止まる。
**リリースには zip と update.json の両方を添付すること**（update.json が無いと、旧版のアプリに更新が知らされない）。

`python tools/update_test.py` — ネットに繋がず、ローカルの偽の配布元で自動更新を通しで確かめる
（更新内容の絞り込み・SHA-256 照合・改ざん/zip slip の拒否・差し替え・失敗時の復元・利用者データを触らないこと・更新後の片付け・CHANGELOG の日英の対応）。
本物の exe の差し替え役は `NonLinearMapper.exe --apply-update --target <配布フォルダ> --pid 0 --lang ja --no-launch`
（`<配布フォルダ>/_update/new/NonLinearMapper/` に置いた exe から起動する）で単体で試せる。
